# 持续集成与发布管理 · 通用搭建指南

> 基于 AutoTestHub 的落地实践，抽象出一套**可复用**的 CI/CD + 制品管理 + 发布管理流程。
> **新增一个仓库 / 新增一个产品**时，照本指南即可快速搭起持续集成、版本发布与制品管理。
> 可运行的完整范例见同目录《14-GitLab-CICD搭建与配置》（AutoTestHub 实战）。

---

## 一、整体能力总览

一套搭好后，你会得到：

```
开发者 push feature → MR → master ──持续部署──▶ 生产环境
                       │                          ▲
                  合入前全套门禁              hotfix 合回
                       │
                 release/* 版本分支(RC/正式) ──▶ 预发布环境 + 出版本包 + 整体测试报告
                       │
                 定时 db/wb (master 快照) / RC (拉 release/rc 分支) ──▶ 制品 + 报告 + 通知
```

- **三层环境**：MR 临时验证环境 / 主干生产环境 / 版本预发布环境，互相隔离。
- **分层流水线**：扫描 → 单测 → 编译 → 出包 → 部署 → 测试 → 上报通知。
- **制品管理**：每个版本出包、登记、可下载、可追溯。
- **发布节奏**：daily build / weekly build / RC / 正式发布，各有触发与门禁。
- **自动化 + 可视化**：定时构建（db/wb 快照、RC 拉分支），结果上报平台 + 即时通知（飞书等）。

---

## 二、核心理念（先理解，再套用）

1. **测试左移**：在 MR（合入前）就把扫描/单测/编译/部署/测试全部跑过，作为合入门禁；合入主干后**不重复跑**，只做部署 + 冒烟。
2. **主干持续 + 版本发布双轨**：master 持续集成（可持续部署）；正式版本走 `release/*` 分支单独出包、单独环境验证。
3. **一切留痕可追溯**：报告、日志、版本号、构建时间、制品一一对应，"没有证据不算通过"。
4. **配置即代码 + 节点可配置**：流水线写在 `.gitlab-ci.yml`；执行节点（Runner）用 tag 路由，换机器只改一处。
5. **环境隔离**：不同用途用不同部署目标（项目名/端口/目录/数据卷隔离），互不干扰。

## 三、前置资源清单（搭一套需要准备什么）

| 资源 | 说明 | 备注 |
|------|------|------|
| **代码仓库** | GitLab 项目（每个产品/模块一个仓库） | 固件/App/测试脚本可分仓 |
| **GitLab Runner** | 至少 1 台 Linux 编译/部署节点；按需加 Windows / 真机 / iOS(macOS) 节点 | 用 **tag** 路由不同任务 |
| **部署目标** | 服务器 + Docker（或 K8s）；区分生产 / 预发布 | 同机可用不同端口+项目名隔离 |
| **制品存储** | GitLab Artifacts（小）/ 对象存储 MinIO（大）/ 自建制品平台 | 见第八节 |
| **通知渠道** | 飞书应用(私信) 或 群机器人 webhook | 见第九节 |
| **访问令牌** | 部署 SSH 私钥、API 只读令牌、写仓库令牌（定时拉分支用） | 全放 CI/CD Variables |

## 四、新增仓库 / 产品 · 复用 Checklist（核心）

> 把这套流程套到一个新仓库/新产品，按顺序做：

1. **建仓库 + 推代码**：GitLab 建项目，本地 `git init` → 加 remote → push。
2. **接入 Runner**：复用现有 Runner（打对 tag）或新装一台；shell/docker executor 按需。
3. **拷流水线模板**：把范例 `.gitlab-ci.yml` 拷过来，**只改这几处**（见 6.3）：
   - 节点 tag（`.linux-node` / `.windows-node` 等）
   - 部署目标（host / 目录 / 端口 / compose 项目名）
   - 制品名、上报地址、通知接收人
4. **配 CI/CD Variables**：部署密钥（`SSH_PRIVATE_KEY` 等，Protected+Masked）、上报令牌、写仓库令牌、通知应用凭证。
5. **设保护分支 + 合并门禁**：`master`、`release/*`(通配) 设 Protected；开启「流水线必须通过才能合并」。
6. **配通知**：上报脚本指向本产品的报告接口/平台 + 通知渠道。
7. **配定时**（可选）：建 Pipeline Schedules（daily/weekly），见第七节。
8. **验证**：提一个 MR → 看门禁全绿 → 合入 → 看部署/通知/报告 → 拉一个 `release/*` 验证出包/预发布。

> 复用的关键：**流水线结构、分支策略、制品/通知套路都不变，变的只是"目标地址 + 节点 + 变量"**。

## 五、分支管理规范（通用）

| 分支 | 用途 | 来源 | 流水线 |
|------|------|------|--------|
| `master` | 主干集成，始终可发布 | feature MR 合入 | 全门禁（合入前）/ 部署（合入后） |
| `feature/*` | 短期开发 | 从 master 拉 | MR 触发：扫描+单测+编译+部署验证+测试 |
| `release/*` | 版本发布线（可维护、可 hotfix） | 从 master 拉 | 编译+出包+预发布+测试+报告 |
| `hotfix/*` | 已发布版本紧急修复 | 从对应 release 拉 | 同 release；修完**合回 release + master** |
| `dev`（可选） | 大团队的不稳定集成区 | 多 feature 汇聚 | 轻量：扫描+单测+编译 |

**命名规范：**
- 功能分支：`feature/<简述>`，如 `feature/login-sso`
- 版本分支：`release/<版本>`
  - 周期 RC（定时自动拉）：`release/rcYYYYMMDDHHMM`（时间命名、无分隔符，如 `release/rc202606261511`）
  - 正式版本：`release/<主.次.修-阶段>`，阶段沿用产品规范（见第六节）
- 修复分支：`hotfix/<版本>`，如 `hotfix/1.2.1`

> **日/周构建不拉分支**：daily/weekly 只是 master 的快照构建（定时直接在 master 上跑、打快照包），不占用分支名；只有 RC 与正式版本才裁 `release/*` 分支走预发布全流程。

> 小团队 2 条长期分支（master + release/*）+ 短期 feature 足够，不必引入 dev。

## 六、硬件产品发布节奏（daily / weekly / RC / 正式）

硬件产品（固件/整机）通常需要**多档构建节奏**，从"每天看健康度"到"正式量产出货"。建议如下（粗略框架，按项目阶段细化）：

| 节奏 | 触发 | 跑在哪 | 版本号 | 制品名 | 测试深度 | 目的 |
|------|------|--------|--------|--------|---------|------|
| **Daily Build（日构建）** | 每天定时 `dailybuild` | master 快照（不拉分支） | `db/YYYYMMDDHHMM` | `autotesthub-db<时间>.tar.gz` | 编译 + 本地实例部署 + 冒烟 + 核心自动化 | 内部研发，**尽早暴露集成问题**，不发布 |
| **Weekly Build（周构建）** | 每周定时 `weeklybuild` | master 快照（不拉分支） | `wb/YYYYMMDDHHMM` | `autotesthub-wb<时间>.tar.gz` | 同 daily（可加专项） | 测试/集成的**里程碑基线** |
| **RC（候选发布）** | 定时 `cut` 自动拉 / 功能冻结后手动 | `release/rcYYYYMMDDHHMM` 分支 | `rc/YYYYMMDDHHMM` | `autotesthub-rc<时间>.tar.gz` | 完整回归 + 专项 + **预发布(独立环境)验证** | QA 验收，**通过即转正式** |
| **正式 / 量产（GA/MP）** | RC 验收通过后手动 | `release/x.y.z-阶段` 分支 | `x.y.z-阶段` | `autotesthub-x.y.z-阶段.tar.gz` | 准出门禁全过 | 出货/上线，**受控发布、可回滚** |
| **Hotfix（补丁）** | 线上/现场问题 | 从 release 拉 `hotfix/x.y.z+1` | `x.y.(z+1)` | `autotesthub-x.y.(z+1).tar.gz` | 针对性回归 + 冒烟 | 紧急修复，**合回 release + master** |

**两类版本号体系（关键区别）：**
- **快照构建**（db/wb）：`<类型>/YYYYMMDDHHMM`，带斜杠前缀（`db/`、`wb/`），由构建 job 现场生成、与 master 当时快照对应；制品文件名把斜杠去掉紧贴前缀（`autotesthub-db<时间>.tar.gz`）。
- **发布版本**（rc / 正式 / hotfix）：从 `release/*` 分支裁出，版本号=分支去 `release/`。RC 时间命名 `rc/YYYYMMDDHHMM`（登记时补斜杠，统一风格）；正式版沿用固件规范 `主.次.修-阶段`：

```
1.0.3-dvt     （DVT 阶段）        1.2.0-pvt     （PVT 阶段）
2.0.0         （正式量产，无阶段）  1.2.1-bugfix  （补丁）
```
> 正式版本号**不混入时间**，干净可比较；时间只出现在 db/wb/rc 这类周期构建里。构建时间另记录在包内 `VERSION.txt` 与报告中。

**节奏与门禁对应：** daily/weekly 失败只通知不阻断；RC 必须满足"安全/核心功能 100% 通过、Blocker/Critical 清零"才能转正式；正式发布走完整准出评审。

## 七、定时自动化（daily/weekly 怎么落地）

用 CI 平台自带的**定时流水线**（GitLab：CI/CD → Schedules；类似 Jenkins 定时触发），无需自建调度：

建 4 个计划，全部 Target=`master`，用变量 `SCHEDULE_TASK` 区分：

| 计划 | cron 示例 | `SCHEDULE_TASK` | 作用 |
|------|----------|-----------------|------|
| Daily Build | `0 2 * * *`（每天 02:00） | `dailybuild` | master 快照：扫描→单测→编译→出包 `db/`→本地实例部署+冒烟+自动化 |
| Weekly Build | `0 3 * * 1`（每周一 03:00） | `weeklybuild` | 同 daily，出包 `wb/` |
| RC 发布 | `0 4 * * 1`（按节奏） | `cut` | 自动拉 `release/rc<时间>` 分支 → 触发版本发布全流程（预发布 + 出包） |
| 清理 | `0 5 1 * *`（每月 1 号） | `cleanup` | 删 N 周前时间命名的 `release/*`（含 rc）；语义正式版本保留 |

**落地要点：**
- 定时 job 用 `$CI_PIPELINE_SOURCE == "schedule"` + `SCHEDULE_TASK` 区分；日/周构建共用一套作业，规则可用 `$SCHEDULE_TASK =~ /build$/` 同时匹配 `dailybuild`/`weeklybuild`。
- **db/wb 直接在 master 上构建**（快照，不拉分支）；**RC 才拉 `release/rc<时间>` 分支**走预发布全流程——两者环境隔离、互不影响。
- 定时跑在主干上，**务必排除"部署生产"等动作**（给相关 job 规则加 `&& $CI_PIPELINE_SOURCE != "schedule"`），避免误发布。
- 自动拉分支 / 删分支用平台 API（需写仓库权限令牌）。

## 八、制品管理

| 方案 | 说明 | 适合 |
|------|------|------|
| **CI Job Artifacts** | 流水线产物直接下载，有保留期 | 起步、零成本 |
| **对象存储（MinIO/OSS）** | 大固件包、长期留存、跨项目共享 | 容量大、要长期 |
| **自建制品平台** | 在自有平台统一登记/下载/检索版本包，和测试报告一个入口 | 要统一视图、可追溯 |

**制品元数据（建议至少记录）：** 版本号、分支/tag、commit、构建时间、大小、下载地址、关联流水线、关联测试报告。

**保留策略：** daily 短期（如 1-2 周）；weekly/RC 中期（数月）；正式版本永久（或打 tag 兜底）。

> 范例（AutoTestHub 规划）：在平台 `/reports` 旁加「制品管理」tab，`package` 阶段出包后把元数据登记到 `/api/artifacts`，前端列表/下载/按版本检索——和「持续集成报告」一个平台。

## 九、通知与可视化

- **结果上报**：流水线收尾把整条 pipeline + 各 job 明细（状态/耗时/覆盖率/日志/链接）汇总，POST 到自有平台展示（如「持续集成报告」页）。
- **即时通知**：飞书应用给**提交人/相关人**发私信，或群机器人 webhook；标题**直接标动作**（"合入 master→部署生产"、"版本发布 x.y.z"、"daily build" 等），一眼看懂。
- **门禁可视**：MR 页显示流水线状态 + 覆盖率，作为合并前置条件。
